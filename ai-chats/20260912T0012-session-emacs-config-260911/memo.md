## 一、动因：稳定性诉求的真正出处（V2.0 结论，已兑现）

表面问题是"升级后很多问题，所以不敢升"。真实结构是：**变更与生效是同一个动作** —— 改配置、升级包、换版本都直接落在日用实例上，唯一恢复手段是整机回退。于是"稳定"只能靠"不改"来买，代价是演化停滞。

chemacs 是当年为这个诉求选的工具，但它没兑现：只切 `user-emacs-directory`（配置文本层），而会坏的是另外三层；连日用入口都不是（systemd 那条链直接落 `/usr/bin/emacs`，靠 `~/.emacs.d` 的 stub 读 profile）。

**→ 2026-09-12 已实际退役**，见 §四。

## 二、认识框架（可继续用）

- **四层隔离模型**：配置文本 / 包树 / Emacs 二进制 / 运行态。谈"稳定"必须先说清隔离哪一层。
- **改变与生效必须分离**：演化随时发生；生效是一次显式的、可回退的、有验收的动作。
- **归属原则**：配置随版本控制（git / yadm 是跨机主通道）、状态随机器（XDG state/cache，不进同步区）、环境随轨（包树与二进制按轨分离）。
- **部署单向**（新增）：产物（`~/.config/emacs`）只从源头（dev）来，**永不在产物里手改** —— 这条把"哪份才是真的"消掉了。
- **可验证性前置**：尺子先于动作；判据事前冻结，事后放宽须显式记录。

## 三、31 移植：难点被重新定位（含 2026-09-12 的修正）

沙箱实测给出与"API 不兼容"相反的结论：**源码层已经兼容**（14 个模块全加载成功、能力探针与 30.2 逐项一致）。解锁它的技术是**把发行版包解到别处直接跑、不安装**。

"换版本必然触发的三类重编译"这条推断，今天被三条实测修正：

- **动态模块**：`rime` 的 `.so` 跨版本可用（两版加载调用均正常）；**但升级包目录会丢模块** —— `vterm` 升级后 `.so` 没了，要在**新包目录**里补编。结论从"换版本要重编"精确为"**升级带原生模块的包之后要重编**"。
- **native-comp**：**换二进制本身不用重编**（本地解包与系统同版本算出的 eln 目录同名）；**换路径必须重编**（`.eln` 文件名含源文件路径哈希）—— 搬到 `~/.cache/emacs/` 那次全量重编 813 个，用受控预热做完。
- **straight**：这次没用上（8 个仓库与远端全同步）。

新增一类此前没记的风险：**退出时编译在飞** → 09:49 那次 SIGABRT（链条：GC 遇致命信号 → 紧急退出 → `kill-emacs-hook` → abort）。处置＝受控预热 + **等编译池排空再退**。

`eln-cache` 里那个高版本目录是**本机** 8-28 那次两小时升级留下的，不是别的机器 —— 所以**其他机器跑什么版本只能现场查**。

## 四、关键取舍（2026-09-12 现状）

**已裁决且已落地（不要重开）**

- 目标：31 下与今天体验一致或更好；不是把包升到最新。
- **三处载体**：日常 = `~/.config/emacs`（yadm 管的**部署产物**）+ 系统 31 + socket `gwp`；开发 = `~/Incoming/emacs-dev` + `gwp-dev`；保底（苟活版）= 旧仓 + 本地解包 30.2 + `gwp30`。三处各有桌面图标。
- chemacs / `~/.emacs.d` stub / `~/.emacs-profiles.el` / `~/.local/bin/emacs` wrapper **已退役**（yadm `2792183`）；autostart 也删了（用户不用开机自启）。
- 系统包位归 31（用户升到 31.1-2）；30 退成本地解包版，只喂保底。
- 用户日用侧不被触碰；保底通道**不依赖 chemacs**（实测过）。
- **订正 V2.0 两条**：① 落点不再是"实体目录，就是 git 仓库本身"——它是部署产物、归 yadm；② "保持 30.2 兼容"**已被决议 12 取代**（演化轨以新为准）。

**AI 的决定（可推翻）**

- 部署机制：`git archive` 导出 + `rsync -a --delete` 镜像；新家不手改。
- socket 名约定：日常 `gwp` / 开发 `gwp-dev` / 保底 `gwp30`；**默认与保底必须不同名**（否则 `emacsclient` 连到谁全靠运气）。
- 不改 `server-socket-dir`。

**暂时采用，不是定论**

- 包策略（跟最新 vs 冻结已验证集合）未裁决。
- 新家包树用"从 dev 复制"而非重装（避开运行时隐式依赖缺件）。
- 保底版与日常版**各有独立运行态**（recentf/history 不共享）—— 退回去时看不到最新最近文件；我认为可接受，未获用户确认。

## 五、方法论沉淀

- 隔离验证 / 二值判据 / 副作用披露 / **实际链接链优先于文档宣称**（V2.0，仍有效）。
- **判据先对齐目标**（用户已写进全局 `AGENTS.md`）：下全称或精确结论、或据其做删除迁移批量动作前，先用边界例、反例或第二来源核验"手里的证据测的就是目标对象与范围"。
- **受控预热**：包树或路径变化后主动编完，并**等编译池排空再退出** —— 把"编译在飞"的窗口从日常使用里挪走。
- **读源码定行为**比试错便宜：启动目录如何选、`custom-save-all` 是否就地编辑、`--eval` 与 init 的先后，今天三处关键判断都是读源码定的。
