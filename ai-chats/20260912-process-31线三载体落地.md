## 二、决策链

### 2.1 两次方向修正（用户提出）

1. **"细节会干扰你，守住大局"**——第一轮我交出的核对表里混着大量会过期的细节（谁推哪个分支、哪条断言会假红），用户叫停：先守动机、目标与大致思路。由此确定本轮的判断顺序：**目标 → 约束 → 现状 → 执行**；细节只在会挡住目标时才升格。
2. **"先形成正式文档，再谈执行"**——动机、原则、目标、方案要先成文并冻结，执行细节由它推导。这条直接否决了"用几句话钉住方向就动手"的急躁版本。

### 2.2 文档分层落定（本轮最大的结构决策）

原先同一批认识散在四处：区域 `AGENTS.md`（定位＋约束＋决策来路）、`PORT-EMACS31.md`（目标＋决议＋施工＋现状）、`registry.md`、以及仓库 `AGENTS.md`。结果是同一件事多份口径，"仓库本体在 `gwp-scratch`"这类错误就是这样长出来的。

落定为五份各守一职：**框架（`docs/framework.md`，裁决源）→ 入口（`AGENTS.md`，纪律与导航）→ 现状（`registry.md`）→ 过程（`PORT`）→ 经验（两份 `learnings.md`）**。备选方案（并进入口、放进 PORT、放进仓库 AGENTS）的否决理由记在框架 §六 与 §七。

### 2.3 代际考古 → 框架 §四

用户提示"翻一翻旧目录，就能理解我的动机"，于是核了 `emacs.old/`（bzr、单文件 `post.el`、Makefile 符号链接安装）、`spacemacs/`、`doom-emacs/`（`doom.note` 315KB ＋ doom CLI）、`gwp/`（chemacs profile ＋ doom 三件套）、`gwp-scratch/`（自建，状态住在仓库里，437M/16047 文件）。结论：

- 这不是"配置坏了"的循环，而是**知识、契约、状态与实现绑死**的循环；每次重建都从零开始，旧 note 只以"历史设置"链接留在原地。
- 因此框架新增 **§四 代际连续性与资产交割**，并给"配置破产"下定义：实现替换时知识、使用契约、恢复能力或日常状态也被迫丢失。

### 2.4 施工计划重写与执行

- 旧 §3.19 的 P0/P1/P2 建立在"`gwp-scratch` 是仓库本体、31 线是它的 worktree"这个已被否定的模型上，只能标废；新 §3.20 用 S0–S5 编号显式脱钩，判据由框架 §四 派生。
- 执行顺序：清卡死的 magit 钩子链 → 退 `gwp-dev` → 活动仓库 `mv` 入区域（不是 fetch 重建，也不是 cherry-pick）→ `daily` 分支 ＋ `emacs-daily` worktree → 隔离验收 → yadm 交还所有权 → 换门牌 → 备份与 tag。逐步结果与证据见 `PORT-EMACS31.md` §3.20 执行记录。

## 四、实验与现场发现（尚未定性，不要当结论用）

1. **socket 文件会消失而进程仍在**：18:20 与 18:25，`/run/user/1000/emacs/` 先后只剩一个 socket，其他在跑的实例失去自己的 socket 文件（`emacsclient` 报 can't find socket，而 `ss` 仍见 LISTEN）。怀疑与"KDE 的 `app-*.service` 单元或某个 `RuntimeDirectory` 被回收"有关，但**未证实**。
2. **两次启动崩溃**：`/usr/bin/emacs-31.1` 以 `emacs '(lisp-form)'`（emacsclient 的 fallback 回退）启动后 SIGSEGV，systemd 存了两份 15M core。与 config 无关的旁证：正常启动路径（裸 `emacs`、`--daemon`）同日多次起停均正常。
3. **启动就绪 30–90 秒**：同配置三次实测 9s／35s／75s；探针必须轮询等待。
4. **`kill-emacs` 可能留下陈旧 socket 文件**，退出后要清；调用前先判 `[ -S … ]`。
