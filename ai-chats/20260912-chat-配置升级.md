### 3. worktree 路径变化可能触发一次 native cache 重建

现在日用代码的逻辑路径是：

```text

```

```text

```

```text

  → 必要时重新 native compile
```

建议定型为：

```text
~/Install/configs/emacs/emacs-dev/       # 同一 Git 仓库，dev 分支
~/Install/configs/emacs/emacs-daily/     # 同仓库 daily 分支的 worktree
~/.config/emacs
  └── symlink → ~/Install/configs/emacs/emacs-daily

~/Install/configs/emacs/gwp-scratch/     # 完全独立的 30.2 保底
```

这里有一个关键修正：

> `~/.config/emacs` 不能直接链接到 `emacs-dev` 主工作树，必须链接到独立的 `daily worktree`。

否则 dev 改一行，日用立即生效，时间差就消失了。

## 日后的日用回路

规则可以非常少：

1. **正常变化只在 `dev` 上做**。
2. `dev` 通过测试并观察后，把 `daily` 分支 fast-forward 到指定提交。
3. 日用只允许做紧急 hotfix。
4. hotfix 尽快回流 `dev`，不要让两个分支长期各自演化。
5. `gwp-scratch` 不参与这条链。

所以你说“`~/.config/emacs` 本身的修改也可以 merge 到 `emacs-dev`”是成立的，但更准确的说法是：

> 修改发生在 `daily worktree`，然后把该分支上的 hotfix 回流到 `dev`；不是修改 symlink 本身。

---

## 这会消掉什么复杂度

### 1. 不再需要 `dev → master` 提升

`gwp-scratch` 的 `master` 现在只表达：

> 一份旧的、能救命的 Emacs 30 配置快照。

它不再是 31 的稳定发布分支，也不需要接收 `early-init.el`。

这样原来最危险的连锁反应自然消失：

```text
dev 合并到 master
  → early-init 进入 30 配置
  → 30 误用 31 的 cache/state
  → 30 读取 31 编译的 .elc
```

现在直接：

```text
dev ──发布──> daily
30 rescue 完全不动
```

这是这次架构简化最有价值的部分。

### 2. 30 不再构成兼容门

Emacs 30 的角色只是：

```text
Plasma 菜单里看得到
点击能启动
gwp30 不抢 gwp
```

它不再要求未来 31 的每个配置改动都兼容 30.2。

这与“30 迟早退役，但短期需要时间差”完全一致。

### 3. yadm 退出 `.config/emacs` 的内容所有权

`~/.config/emacs` 改成 symlink 后，建议：

- yadm 不再跟踪 `.config/emacs` 下的配置文件；
- 不把 symlink 当作跨机器部署入口；
- 旧的 yadm 提交保留，作为一次性回退备份；
- Git worktree 成为 31 配置的唯一真源。

你已经明确“不太需要考虑其他机器”，因此这里不必再为 yadm 设计复杂的 bootstrap 流程。

---

## 仍然不能省掉的两层隔离

软链接只解决**配置代码的版本切换**，不会改变包树与运行态：

```text
31 dev:
  ~/.cache/emacs-dev/
  ~/.local/state/emacs-dev/

31 daily:
  ~/.cache/emacs/
  ~/.local/state/emacs/

30 rescue:
  gwp-scratch 自己的旧包树与状态
```

特别是：

- `elpa/`
- `straight/`
- `.eln`
- `vterm-module.so`
- `rime` 动态模块
- `custom.el`
- `history`
- `recentf`

仍然不能在 dev 和 daily 之间自动共享。

因此日后分两类：

```text
只改配置代码
  → daily worktree 更新即可

新增/升级包、原生模块变化
  → 先准备 daily 的包树与模块
  → 再更新 daily worktree
```

这不是额外的工程化，而是为了避免 dev 的实验污染日用，必须保留的最小边界。

---

## 两条小尾巴怎么排

### 全量 native compile

这个不应该现在单独完成。

当前日用源路径是：

```text
~/.config/emacs
```

改成 symlink 后，实际 worktree 路径会变成：

```text
~/Install/configs/emacs/emacs-daily
```

此前已经确认 `.eln` 文件名包含源路径哈希，因此这次切换很可能会触发一批新的 native compilation。

正确顺序是：

```text
先固定 daily worktree 路径
  → 切换 ~/.config/emacs symlink
  → 启动 daily
  → 受控 native prewarm
  → 等编译池排空
  → 再退出或重启
```

所以现在把旧路径的 native 编译补完，收益很低，甚至可能做两遍。**它应当并入 worktree 迁移后的收尾步骤。**

### 无名 systemd Emacs

它与 Git 架构无关，不应阻塞迁移。

可写模式下只需要：

1. 确认并关闭那个没有 socket 归属的 `/usr/bin/emacs` 实例；
2. 对已经删除的 `app-emacs@autostart.service` 执行一次 `systemctl --user daemon-reload`；
3. 不碰 `gwp`、`gwp-dev`、`gwp30` 三个有效实例。

当前仍是只读 / deep-think 模式，我没有动它们；这件事可以作为独立收尾，不需要重新设计。

---

## 真正的下一步，不是 merge，而是迁移

可写后，施工顺序应当是：

```text
1. 关闭 gwp-dev，保留 gwp30
2. 把 emacs-dev 放到 Install 下的最终位置
3. 从当前已部署提交创建 daily worktree
4. 对比 daily worktree 与当前 ~/.config/emacs
5. 先用临时 socket 启动验证
6. 停 gwp / gwp-new
7. 保留旧 ~/.config/emacs 目录作为回退副本
8. 创建 ~/.config/emacs → emacs-daily 的 symlink
9. 让 yadm 放弃该目录的内容所有权
10. 启动 gwp，跑验收清单
11. 在最终路径上做 native prewarm
```

回退面也比之前简单：

```text
删除 symlink
  → 恢复旧 ~/.config/emacs 目录
  → 重启 gwp
```

运行态和包树仍在各自的 XDG 目录里，不需要跟着配置回退。

## 最终定案

我建议现在冻结以下方向：

> **31 用同一 Git 仓库的 `dev` 与 `daily` 两个 worktree；`~/.config/emacs` 只作为 daily worktree 的 symlink；30 的 `gwp-scratch` 原地保留、完全不跟随；不再做 `dev → master` 提升。**

这比当前方案少了一层发布复制，也没有把即将退役的 30.2 拉进 31 的演化回路。

当前高把握结论是：**架构方向没有原则性问题。**  
唯一需要现场验证的边界是：symlink 切换后 native cache 的实际重建量，以及 yadm 放弃该目录所有权后的工作树是否干净。这两项都是一次性迁移问题，不是架构缺陷。
